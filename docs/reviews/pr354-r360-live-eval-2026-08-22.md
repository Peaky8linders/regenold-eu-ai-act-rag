## 2. L1 — `/healthz/llm` is a false green (Critical)

`_degraded_to_bedrock` decides "is leg 2 carrying traffic?" from `is_bedrock_provider_enabled()`:

```python
# app/main.py:1014-1022
    from app.llm.bedrock_client import is_bedrock_provider_enabled
    armed = is_bedrock_provider_enabled()
except Exception:
    armed = False
if armed:
    base["llm_ok"] = True
    base["detail"] = f"primary offline ({detail[:120]}); bedrock fallback active"
```

And `is_bedrock_provider_enabled` is a **pure configuration-presence check** — it never
dials anything:

```python
# app/llm/bedrock_client.py:853-864
def is_bedrock_provider_enabled() -> bool:
    if _resolve_bearer_token():           return True
    if os.getenv("AWS_BEDROCK_API_KEY", "").strip():  return True
    if (os.getenv("AWS_ACCESS_KEY_ID", "").strip()
        and os.getenv("AWS_SECRET_ACCESS_KEY", "").strip()): return True
    return False
```

Sixty lines later the *same handler* assembles `stage2_transport.stats` from actual dials.
The two never cross-check, and **in production they already disagree inside one response body.**

The docstring names the exact failure it then commits:

> an uptime monitor alerting on `llm_ok` cannot tell the difference between
> "degraded but serving" and "serving deterministic fallback only"

R360.9 fixed the false-*negative* (`llm_ok:false` while Bedrock served) and shipped the
false-*positive* in its place. The blind spot moved one leg down; it did not close.

**Fix.** The data is already in the module. Treat `fallback_attempts > 0 and fallback_ok == 0`
as an outage, not as degradation.

## 3. L2 — the boot guard seeds over a live graph (Critical)

`GraphClient.execute_read` **never raises**; it logs and returns `[]`:

```python
# app/graph/client.py:202-203
logger.warning("Neo4j execute_read failed: %s", exc)
return []
```

Both auto-seed reads call it. The full path:

```
read KBMetadata  ── client.execute_read ──┐         app/main.py:541
   ├─ TIMEOUT            → skip-unverified            ✅ R360.6 fixed this
   └─ READ FAILURE       → returns []
        → current_seed = ""
        → the seed_version match at :573 is NEVER REACHED
        → `if not current_seed:` branch                app/main.py:596
             └─ node count ── client.execute_read ──   app/main.py:606
                  └─ READ FAILURE → [] → _node_count = 0
                       → falls past `if _node_count > 0`
                       → reason = "graph_empty"
                       → SEEDS OVER THE LIVE GRAPH
```

R360.6's own comment asserts the premise that makes this safe, and the premise is false:

> ONLY the budget case is swallowed here. **A genuine exception from `execute_read` still
> propagates** to the top-level handler below

`execute_read` does not raise, so nothing propagates. R360.6 correctly closed the *timeout*
hole and left the *read-failure* hole open while documenting it as closed.

Two aggravating facts:

* The `seed_version` match cannot protect you, because the version read is the **first**
  thing that fails.
* During the graph-dead arm of this evaluation, `execute_read failed` was logged **246 times**.
  This transient is not hypothetical on this deployment.

**Fix.** `client.execute_read_strict` — added by this very PR at `client.py:210`, and with
**zero non-test call sites in `app/`** — raises. Use it at both `:541` and `:606`.

**The covering test takes the wrong branch.** `tests/test_r360_6_auto_seed_guards.py:98`
uses a double whose `_read` *raises*. Production returns `[]`. One screen over, the PR's own
`tests/test_r360_12_verified_bug_fixes.py:100` asserts `client.execute_read(...) == []`
under a raising `_run_read`. **Two test files in one PR encode contradictory models of the
same method, and the seeder test picked the wrong one.** Keep both; add a third whose double
*returns* `[]`.

| reference_correctness | 54 | 66 | **0.4500** |
| citation_faithfulness | 49 | 71 | **0.4083** |

| axis | pass | fail | pass rate |
|:--|--:|--:|--:|

| reference_correctness | 47 | 73 | **0.3917** |
| citation_faithfulness | 51 | 69 | **0.4250** |

### The comparison — and why it is a NULL, not a regression

Aggregate deltas look like the graph costs reference precision (−0.0583). **The paired test
says otherwise.** Both arms cover the same 120 row ids, so a per-row sign test is available
and is the correct instrument:

| axis | both pass | neither | DEAD-only | LIVE-only | discordant | flip rate | exact p |
|:--|--:|--:|--:|--:|--:|--:|--:|
| answer_correctness | 48 | 57 | 7 | 8 | 15 | 0.12 | **1.0000** |
| reference_correctness | 42 | 61 | 12 | 5 | 17 | 0.14 | **0.1435** |
| citation_faithfulness | 40 | 60 | 9 | 11 | 20 | 0.17 | **0.8238** |

**No axis reaches significance.** The −0.0583 reference delta is p = 0.14 — a directional
hint at most, and it must not be reported as "the graph costs precision".

**The load-bearing number is the flip rate: 12–17 % of rows change verdict between the two
runs.** That is the measured noise floor of this instrument at n = 120 against
non-deterministic Stage-2 generation. It means **any aggregate delta below roughly ±0.06 on
this harness is indistinguishable from generation noise**, which is exactly the size of the
effect being chased. This extends `project_easyhard_ab_noise_floor_n40` with a concrete
figure at n = 120: the noise floor did not collapse by tripling n, because the variance is
per-row generation variance, not sampling error.

Practical consequence: to resolve an effect this size on the reference axes you need either
a position-swapped **pairwise** judge (which shares judge variance rather than differencing
it — the `ab_judge` design) or a zero-variance replay. Two independent live runs will not do
it at any n this project can afford.

Substantively: the graph delivers ~15.9 k characters of context per request and **does not
measurably move any judged axis**. That is consistent with `AGENTS.md` invariant #3 — the
graph is additive, non-citable Stage-2 context, not a ranker.

Over-citation dominates the reference failures in **both** arms, unchanged by graph
availability. The graph-live arm adds a notable mode: *"over-citation: parent article cited
alongside specific paragraph already covering…"* — the parent+leaf duplication recorded as
D1 in `project_regenold_top_defects`.

## 6b. THE HEADLINE — the fallback leg is a 27-point answer-correctness cliff

After the operator re-authenticated Claude Max mid-session, the primary leg came back and the
same 120-row sample was re-run **on the tunnel**, graph live, judged identically.

| axis | Qwen fallback (graph dead) | Qwen fallback (graph live) | **Claude Max primary** | Δ vs best fallback |
|:--|--:|--:|--:|--:|
| answer_correctness | 0.4583 | 0.4667 | **0.7333** | **+0.2666** |
| ↳ mean_factual_score | 0.7637 | 0.7787 | **0.9384** | +0.1597 |
| reference_correctness | 0.4500 | 0.3917 | 0.4583 | +0.0083 |
| citation_faithfulness | 0.4083 | 0.4250 | **0.6417** | **+0.2167** |

Paired sign test, Claude Max vs Qwen (both graph-live, same 120 row ids):

| axis | both | neither | ClaudeMax-only | Qwen-only | exact p |
|:--|--:|--:|--:|--:|--:|
| answer_correctness | 52 | 28 | **36** | 4 | **< 0.000001** |
| citation_faithfulness | 41 | 33 | **36** | 10 | **0.000156** |
| reference_correctness | 38 | 56 | 17 | 9 | 0.1686 (n.s.) |

**These are 4× the measured noise floor (§6) and overwhelmingly significant.** Switching from
leg 2 to leg 1 fixes **36 of 120 rows** on answer correctness while breaking 4.

Three consequences:

1. **The Bedrock fallback is not graceful degradation. It is a cliff.** `stage2_policy`'s own
   `stage2_fallback_model` docstring warns that "an answer served from leg 2 is not the answer
   any A/B measured". It now is measured: **−0.27 answer correctness, −0.22 citation
   faithfulness.** Leg 2 keeps the service *answering*; it does not keep it *correct*.

2. **This makes L1 (the `/healthz/llm` false green) materially worse, not merely untidy.**
   The probe reports `llm_ok: true` from a credentials check while the service serves from the
   leg that is 27 points worse. The one signal an operator would page on cannot see the
   largest quality regression the system can experience.

3. **Over-citation is model-independent.** Reference correctness is flat across all three arms
   (0.39–0.46) and the only non-significant axis. A frontier model does not fix it. That is
   direct confirmation of `project_r317_overcitation_five_families`: **the lever is the
   ranker, not the generator and not a trimmer.** The failure modes are identical in kind on
   Claude Max — "Annex III lists categories but does not itself…", "Article 49 governs
   registration, not classification", "parent article cited alongside specific paragraph
   already covering it" (the D1 parent+leaf duplication).

Batch shape also shifts the way a healthy primary should: `answer_chars` 657 → **1130**,
`n_refs` 2.77 → 2.93, `vs_july7_ref_jaccard` 0.545 → 0.583, `tone` 1.0, refusals 0,
`stage2_landed_rate` 0.775, latency p50 15.9 s.

**Production recovery was verified end-to-end.** Before re-auth, asked for *deployer*
record-keeping duties, production returned Article 6(2)'s text about Annex III classification
with a deterministic-fallback warning. After: a correct grounded answer — logs under the
deployer's control, retained **at least six months**, Article 26 read with Article 12 —
and `/healthz/llm` reporting `provider: openai_wrapper`, `detail: "ok"`.

| `render_kg_context` chars | **35,238** | 939 |

**37× more grounding context, and 3× faster** — a dead host costs ≈8.8 s per question in
connection retries. This also corroborates the arm labelling: the graph-LIVE arm's p50 was
11.6 s against graph-DEAD's 14.8 s, the same direction.

* graph ON: `['Article 18', 'Article 19', 'Annex IV']` — 3 refs
* graph OFF: `['Article 16','Article 19','Article 11','Article 17','Article 18','Article 47']` — 6 refs

## 8. L7 — the contract A/B is under-warned in the runbook

`docs/LIVE-EVAL-RUNBOOK.md` warns that with the tunnel **healthy** both arms answer from the
tunnel and the A/B reads ~0 by construction. True — but incomplete.

Measured here, two-sided, with the tunnel genuinely down:

| arm | answer | references | counters |
|:--|:--|:--|:--|
| `STRICT_TRANSPORT=1` | identical | `['Annex III','Article 43','Annex VI']` | `refused: 0` |
| `STRICT_TRANSPORT=0` | identical | `['Annex III','Article 43','Annex VI']` | `refused: 0` |

**Byte-identical, and `refused` is 0 in both.** Groq is the *tertiary* leg: when Bedrock
succeeds at leg 2, the legacy chain never reaches Groq either, so the two arms are
indistinguishable. The seal is observable **only when both permitted legs fail** — which is
why production shows `groq: 2` and a healthy-Bedrock box shows `0`.

So the A/B reads ~0 in *two* regimes: tunnel healthy, and tunnel-down-but-Bedrock-healthy.
The second is the common one. An operator following the runbook on a working box would
reasonably conclude the flag is inert — the R329 trap, arrived at from the opposite
direction.

**Fix.** State in the runbook that the tunnel-down arm must *also* disarm Bedrock
(`AWS_BEARER_TOKEN_BEDROCK=` blank) for the contract to be visible at all.
