### [I1 / P1] “Not high-risk” is treated as proof that chatbot transparency duties do not apply

- **File:** `app/engines/_graph_rag_impl.py:5447` (admission), `:5487` (incomplete exclusion), `:7332` (fixed answer).
- **Bug:** The new exclusion-shaped minimal-risk detector accepts “If a chatbot that interacts directly with people is not high-risk, do any duties still apply under the EU AI Act?” Its limited-risk exclusion recognizes explicit transparency/disclosure vocabulary, but does not recognize the stated direct-interaction function.
- **Observed result:** HTTP 200 supplies the residual-class answer describing systems as “nor subject to the Article 50 transparency duties.” It never answers the stated chatbot's Article 50(1) disclosure duty. The authoritative intercept prevents normal generation from correcting the classification.
- **Impact:** An ordinary compliance question receives an authoritative answer that omits an applicable mandatory duty.
- **Suggested fix:** Do not infer residual-tier membership solely from absence of high-risk classification. Assess Article 50 functions separately before selecting this fixed answer.
- **Provenance:** New relative to the initial review base; the exact question did not match the base detector.
- **Confidence:** High (100%). **Found by:** Logic/correctness; independently reproduced by verifier.

### [I2 / P1] An ancillary preparatory task overrides the explicit profiling exclusion

- **Bug:** `_art63_question_describes_another_system` returns early when it sees a procedural/preparatory task, before respecting a described substantive profiling function.
- **Reproduction:** “Can an AI system that profiles credit applicants benefit from the Article 6(3) derogation if it also performs preparatory tasks?”
- **Observed result:** HTTP 200 begins “No. Structuring or deduplicating information is a narrow procedural task, so the system … is not high-risk”, then adds that the derogation never applies where the system profiles natural persons. It invents a task and contradicts its own classification.

- **Suggested fix:** Give profiling/substantive-use exclusions precedence over ancillary-task matches. Reserve the fixed non-high-risk verdict for facts that actually establish its task and conditions.

- **Confidence:** High (100%). **Found by:** Logic/correctness; independently reproduced by verifier.

### [I5 / P2] Hard-batch checkpoints combine one turn's answer with another turn's references

- **File:** `evals/regenold/run_official_batch.py:956` in reviewed main (the integration adds skip-provenance lines above it).
- **Bug:** `pred_answer = ans2 or ans1` and `pred_refs = refs2 or refs1` select their source turns independently. A successful pushback with an empty reference list is valid data, not a missing answer.
- **Reproduction:** Run real `_run_hard` with a fake poster returning turn 1 `{"answer":"Turn1","references":["Article 13"]}` and turn 2 `{"answer":"Corrected answer without citations","references":[]}`.
- **Observed result:** The checkpoint reports `graded_turn="pushback"`, the corrected `pred_answer`, and `pred_refs=["Article 13"]`, even though `pushback_refs=[]`. Its `_row_metrics(ans2, refs2)` uses the genuinely empty list, so prediction and score inputs also disagree.
- **Impact:** Consumers of the checkpoint can credit citations the graded answer never emitted, masking a real reference-loss regression.
- **Suggested fix:** Select answer, references and provenance atomically using the same landed-turn condition, e.g. `refs2 if ans2 else refs1`.
- **Provenance:** Pre-existing.
- **Confidence:** High (100%). **Found by:** Contract/integration; independently reproduced by verifier.

### [I6 / P2] Empty HTTP-200 completions keep the batch failure guard healthy

- **File:** `evals/regenold/run_official_batch.py:610`; engine rejection at `app/engines/_graph_rag_impl.py:12027`.
- **Bug:** `guarded_complete` calls `transport.record_ok()` on every response with no `error`, even when the completion is empty and the real engine rejects it as degenerate. Each such response resets the consecutive-failure counter before the bounded rescue/abort can run.
- **Reproduction:** Install the real transport guard with `max_consecutive=2`; supply primary `OpenAIWrapperResponse(text="", completion_tokens=1, model="test")` responses and deterministic row provenance. Twelve consecutive degenerate rows complete without an abort.
- **Impact:** A batch can continue grading deterministic fallback drafts throughout an unusable-primary outage despite its advertised failure limit. Existing tests for empty liveness pings do not exercise empty ordinary completions.
- **Suggested fix:** Count empty/degenerate primary completions as failures using rejection semantics consistent with the engine.
- **Provenance:** Pre-existing guard gap retained by the new rescue logic.
- **Confidence:** High (100%). **Found by:** Contract/integration; independently reproduced by verifier.

### [I8 / P2] The first denied Bedrock model can bypass healthy lower models

- **File:** `app/engines/_graph_rag_impl.py:843`, `:862`; inner cross-provider hop at `app/llm/bedrock_client.py:1567`.
- **Bug:** The outer model-chain loop calls `complete_with_fallback(..., fallbacks=())` per candidate. The empty tuple suppresses inner model fallbacks but does not suppress its wrapper hop. A wrapper success is accepted before the outer loop tries the remaining Bedrock candidates.
- **Reproduction:** Use the real outer and inner orchestration with mocked transports: ordered models are denied Opus then healthy Qwen; Opus returns normalized `api_access_denied: no entitlement`, while the wrapper succeeds. Only Opus is called on Bedrock; Qwen is never attempted.
- **Observed result:** Wrapper text is returned with trace `stage2_model=wrapper:test provider=bedrock complex=False`.
- **Impact:** A denied preferred model routes away from an available Bedrock tier, and provider provenance misidentifies the resulting serve. The R464 diagnostic detects masking, but does not fix this serving-path ownership conflict.
- **Suggested fix:** Give one layer ownership of model-chain traversal and defer cross-provider fallback until that complete chain is exhausted. Preserve actual provider provenance.
- **Provenance:** Pre-existing integration defect retained through R464.
- **Confidence:** High (100%). **Found by:** Contract/integration and coordinator; independently reproduced by verifier.
