A caller diffing an `ab_judge` sidecar against a `pairwise_from_answers` sidecar for the same kind of run will find one has the field and the other doesn't, with no error to flag it.

## `recall_available` computed two different ways for the same row, prompt vs. post-processing disagree
- file: `evals/judge/legal_v2.py:452` (prompt) vs `evals/judge/legal_v2.py:739` (post-processing context)
- bug: `render_reference_correctness` decides whether to tell the judge "recall is assessable" using `recall_available = bool(gold_map or r.get("independent_gold_context"))` (line 452) — true whenever `gold_map` has ANY key, regardless of whether the resolved text is empty. `_prepare()` computes the metadata flag actually used by `_postprocess_reference_correctness` (via `ctx["recall_available"]`, consumed at line 1269) as `any(str(text).strip() for text in gold_map.values())` (line 739) — true only when at least one ref's text actually resolved. Since `_resolve_provision_texts` (line ~320) always inserts a key for every ref even when the text doesn't resolve (empty string value), and `_block_from_map` renders those as `"[ref] (no verbatim text resolved...)"`, a row whose only gold refs are non-existent/unresolvable provisions gets `recall_available=True` in the prompt (line 452) but `recall_available=False` in post-processing (line 739/997).
- impact: The judge is instructed "Assess missing governing provisions against the independent gold block" (line 456) on a row where the gold block is actually empty text, wasting a call and risking the model fabricating `missing_governing` entries from memory against an explicitly-labeled "(no verbatim text resolved)" block — while post-processing then discards whatever it said anyway (`missing_raw = [] if not recall_available`, line 969, and `recall = None`, line 987). The two flags meant to represent one concept ("do we have real gold text") diverge at exactly the boundary this refactor was built to handle (rows with unresolvable/absent gold), so the prompt's stated contract with the judge doesn't match what the code will do with the reply.
- fix: Compute `recall_available` once (e.g. in `_prepare()`) and pass it into `render_reference_correctness` instead of recomputing it inside the render function from `gold_map`'s key-presence; use the same `any(text.strip()...)` check in both places.
- confidence: 70

## `swap_consistency_rate` counts coincidental judge errors as "agreement"
- file: `evals/harness/ab_judge.py:283-294`
- bug: `_pairwise_verdict_detail` calls `_judge_one` twice (order 1 and order 2). `_judge_one` (line 247-255) collapses ANY judge/parse failure to `"tie"` with no way for the caller to distinguish a real tie from an error. `agreed = (w1 == w2)` (line 292) then treats two independent failures (both returning `"tie"` for unrelated reasons — e.g. a transient `api_status_500` on each call) as if the two position-swapped orderings "agreed," inflating `swap_agreements` / `swap_consistency_rate` (the exact metric R416 added to measure genuine judge self-consistency).
- impact: On any run with a non-trivial judge error rate (the repo's own history documents ~40% per-call failure rates over the tunnel, see `legal_v2.py`'s `_DEFAULT_MAX_RETRIES` docstring), `swap_consistency_rate` will read artificially high, masking real position-bias/inconsistency behind coincidental double-failures. This is silent — there's no separate counter for "agreed because both errored" vs "agreed because the judge was actually consistent."
- fix: Have `_judge_one` (or a wrapper) surface whether the call errored, and only count `agreed=True` when both orderings produced a genuine `"A"`/`"B"`/`"tie"` verdict from a successful call, not from an error fallback.
- confidence: 60
