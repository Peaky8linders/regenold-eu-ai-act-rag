## `--provider openrouter` silently runs over the Claude Max wrapper instead
- file: `evals/judge/legal_v2.py:1620`
- bug: `_assert_claude_max_transport` now treats `provider in ("bedrock", "openrouter")` as pre-approved, printing `f"[legal_v2] provider={provider} active"` and returning immediately with no credential/transport check. But `_resolve_caller` (`evals/judge/runner.py:721-751`), which `legal_v2.run()` calls right after (`evals/judge/legal_v2.py:1671`), has no branch for `"openrouter"` at all — it only special-cases `"anthropic"`, `"groq"`, `"gemini"`, and `"bedrock"`, then falls through to `return lambda p: _call_judge_sonnet(...)` (`runner.py:751`) for "wrapper" or *anything else*, including `"openrouter"`.
- impact: Running `python -m evals.judge.legal_v2 --provider openrouter ...` prints a message implying OpenRouter is active, but every judge call is actually dispatched over the Cloudflare-tunnel/Claude Max wrapper — the exact transport `openrouter` was added to avoid sharing with Stage-2 (CLAUDE.md: "No Parallel Wrapper Jobs"). The run silently competes with any concurrent Stage-2 wrapper traffic, and any provenance recorded from this run ("judged via OpenRouter") is false. No test in scope exercises this path (`tests/test_legal_v2_judge.py` never calls `--provider openrouter` end to end), so nothing catches it.
- fix: Add an explicit `"openrouter"` branch to `_resolve_caller` (a real `_call_judge_openrouter`), or reject `"openrouter"` in `_assert_claude_max_transport` until that caller exists.
- confidence: 90

## New judge axes' JSON schemas are invisible to the multi-object recovery pass
- file: `evals/judge/runner.py:571-572`
- bug: `_parse_judge_json`'s pass-4 fallback (used when the reply isn't cleanly fenced or isn't valid JSON on its own, e.g. a leading "thinking" sentence — the exact case the function's docstring calls out) only accepts a scanned candidate object if it contains at least one of `target_keys = {"verdict", "winner", "propositions", "classifications", "citations", "sentence_count", "issues", "criteria_analysis", "candidate_a_audit"}`. The three axes added in this same diff in `evals/judge/legal_v2.py` use different top-level schema keys: `answer_crag_fine` → `score`/`class`/`rationale`/`missing`/`hallucinated` (`legal_v2.py:789`), `answer_faithfulness` → `claims` (`legal_v2.py:794`), `answer_relevancy` → `relevancy` (`legal_v2.py:795`). None of these appear in `target_keys`.
- impact: For these three axes, any reply that needs the multi-object recovery path (prose before/after the JSON, no fence) is rejected outright with `{"judge_error": "unbalanced_json", ...}` even though a valid, complete JSON object was found and parsed successfully by the scanner — it's discarded purely because its keys aren't allow-listed. This silently shrinks n / biases the sample for `answer_crag_fine`, `answer_faithfulness`, and `answer_relevancy` toward replies that happen to come back cleanly fenced or with no leading text, exactly the failure mode this function exists to rescue. No test in scope drives a prose-wrapped reply through `_parse_judge_json` for any of these three axes (`tests/test_r359_crag_fine_axis.py` and `tests/test_r360_hypa_ref_free_axes.py` call the `_postprocess_*` functions directly with hand-built dicts, bypassing the parser).
- fix: Add `"score"`, `"class"`, `"claims"`, `"relevancy"` (or derive `target_keys` from `legal_v2._AXIS_KEYS`) to the allow-list in `_parse_judge_json`.
- confidence: 80

## Bedrock credential check dropped from the judge's upfront transport assertion

- impact: A misconfigured Bedrock run (no `AWS_BEARER_TOKEN_BEDROCK`/`AWS_BEDROCK_API_KEY`/keys) no longer fails fast with an actionable message; it proceeds through the whole row set, and every row's `answer_correctness`/etc. axis independently returns `{"judge_error": "bedrock_not_configured"}` from `_call_judge_bedrock` (`runner.py:282-283`) only after doing the (wasted) per-row setup work. - confidence: 65

## Per-row transport provenance silently reads "not fallen back" when the snapshot is unobservable
- file: `evals/harness/easyhard_ab.py:209-226`
- bug: `_transport_snapshot()` swallows any exception from importing `app.llm.stage2_policy` / calling `transport_stats()` and returns `{}`. `_row_transport(before, after)` then computes every delta as `0 - 0 = 0` and sets `"stage2_fell_back": bool(fallback_ok) = False`. Because the key IS present (just `False`), `_fallback_served` (`easyhard_ab.py:~245`, whose own docstring says "a row that cannot be shown to have been tunnel-served must not be counted as one") takes the `"stage2_fell_back" not in row` branch as `False` and treats the row as confirmed tunnel-served — the opposite of its stated conservatism. This is explicitly pinned by `tests/test_r416_gate_provenance_and_dotenv.py::test_row_transport_is_inert_when_counters_are_unobservable`, which asserts `stage2_fell_back is False` for the unobservable case.
- impact: If `transport_stats()` becomes unobservable mid-run (import error, refactor, etc.), `_exclude_fallback_rows` will never drop any row, and `rescued` in `main()` (`easyhard_ab.py:~1030`) will stay `False` — the run is not falsely "rescued" here. The residual risk is narrower than it first looks because `gate_validity.assess`'s arm-level `stats_error` check (`gate_validity.py:96-102`, `:457-459`) is a redundant, independent backstop that still voids the run when the same import fails. Reported because the per-row helper's behavior directly contradicts its own docstring guarantee and the dedicated test pins the contradiction rather than the guarantee — a future caller that trusts `_fallback_served` in isolation (without the arm-level backstop) would get a false "tunnel-served" signal.
- fix: Have `_transport_snapshot()`/`_row_transport` distinguish "observed zero fallback" from "unobservable" (e.g. return `None`/omit the key on exception) so `_fallback_served`'s missing-key branch actually triggers.
- confidence: 60
