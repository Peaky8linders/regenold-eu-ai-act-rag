## Unescaped `references` field lets a crafted citation break out of the pairwise-judge XML block
- file: `evals/harness/pairwise_prompts.py:54,58`
- bug: `_ab_block` escapes the answer text with `_escape_xml` (added in this diff specifically to stop candidate content from being confused with prompt structure — see `test_xml_escaping` in `tests/test_judge_adversarial_remedies.py`), but the sibling `<references>` element is built with the raw, unescaped `str(refs_a or [])` / `str(refs_b or [])` (`pairwise_prompts.py:54` and `:58`). `refs_a`/`refs_b` are not judge-authored or gold data — they come straight from the live app's HTTP response (`evals/harness/ab_judge.py:222`, `refs=list(body.get("references") or [])`), i.e. from the end-to-end Stage-2 pipeline processing arbitrary user-supplied `messages`. This repo's own history (R361, R365, R413 "the wire references list is recomputed from the final Stage-2 prose" by passes that promote text the prose names) documents that malformed/unexpected reference strings do reach the wire under adversarial or edge-case input, and the probe corpus itself contains adversarial pushback/injection rows.
- impact: A crafted or model-influenced reference string containing `</candidate_a>`, `</candidate_b>`, or a fake `<references>...</references>` block is inserted into the pairwise-judge prompt verbatim inside `<references>...</references>`, adjacent to the just-escaped, supposedly-isolated `<answer>` block. Because the escaping was added precisely to stop candidate content from being mistaken for prompt structure, this reopens the exact class of "candidate output masquerading as judge-prompt structure" injection for one of the two fields that flow into the same block — able to mis-attribute content between candidate A/B or splice extra "instructions" into what the judge treats as trusted framing. This pairwise judge (`ab_judge.py`) backs the project's declared sole merge gate, so a manipulated verdict here directly affects what ships.
- fix: Route `refs_a`/`refs_b` through `_escape_xml` (or a per-element escape + safe join) the same way `answer_a`/`answer_b` are handled before interpolating into `<references>`.
- confidence: 75

## `_assert_claude_max_transport` grants `openrouter` a no-questions-asked pass, but the caller resolver silently ignores it and dispatches over the wrapper instead
- file: `evals/judge/legal_v2.py:1620`
- bug: `_assert_claude_max_transport` now short-circuits with `if provider in ("bedrock", "openrouter"): print(...); return` (`legal_v2.py:1620-1623`), removing both (a) the prior Bedrock credential check (`is_bedrock_provider_enabled()`) that used to hard-refuse a misconfigured run instead of silently scoring every row as `judge_error`, and (b) any check at all for `openrouter`, which AGENTS.md/CLAUDE.md explicitly state "this repo has no OpenRouter path and must not grow one." `evals/judge/runner.py::_resolve_caller` (`runner.py:721-751`), which `legal_v2.run()` calls right after this guard (`legal_v2.py:1671`), has no `"openrouter"` branch at all — it falls through to the final `return lambda p: _call_judge_sonnet(...)`, i.e. the Claude Max wrapper. So the transport gate that is supposed to make an operator's provider choice authoritative (and that this same file's own comments call out as protecting against unintended per-token billing / unauthorized destinations) now accepts `--provider openrouter` as a fully-verified, no-confirmation-needed choice while the code silently substitutes a completely different transport.
- impact: An operator who runs `--provider openrouter` gets no error, sees `"[legal_v2] provider=openrouter active"`, and reasonably believes evaluation data (question text, verbatim Act text, predicted/gold answers) is being routed to OpenRouter — but it is actually sent over the Claude Max wrapper/tunnel instead, silently defeating the purpose of the transport gate (which exists to make the actual data destination match what was authorized/confirmed). Symmetrically, the Bedrock branch no longer verifies credentials before proceeding, so a misconfigured Bedrock run silently degrades into scoring every row as `judge_error` rather than failing fast — reintroducing the exact failure mode the removed check's comment describes ("Refusing rather than scoring every row as judge_error").
- fix: Restore the Bedrock credential check before granting Bedrock a pass-through, and either implement a real `openrouter` branch in `_resolve_caller`/`_call_judge_*` or remove `"openrouter"` from the exempted providers in `_assert_claude_max_transport` (and from the `--provider` choices) until it exists.
- confidence: 70
