## Executive Summary

R360 does the thing it set out to do: `app/llm/stage2_policy.py` is a single, readable
source of truth for the Stage-2 transport contract, five genuine escape hatches are closed,
and the hoisted `_try_bedrock_fallback` fixes a leg that was measurably dead on the most
common tunnel failure. The deterministic path is byte-identical to `main` and the strict
default is two-sided tested. That part is good work.

The defects cluster in one place, and it is the same place the PR's own rationale identifies
as the thing that matters: **the instruments**. `stage2_policy.py:33-40` argues the contract
must be *counted* because "a routing lever that reads plausibly in the diff and makes zero
calls is indistinguishable from one that works." Fifteen of the twenty findings below are
cases where a counter, a guard, or a test does not measure what it claims:

* `fallback_ok` increments for Bedrock answers that are then discarded (**I5**), and two of
  the three fallback exit paths record no result at all (**I5**, **I6**) — so
  `attempts == ok + failed` is not an invariant on either leg.
* An empty-but-successful wrapper reply is counted `primary_ok` and, because `"" is not None`,
  **skips the Bedrock leg entirely** (**I2**) — a fourth failure mode the hoisted fallback
  does not reach, and the one the repo has already observed in production (Issue #42).
* The fusion panel and its judge dial `OPENAI_API_BASE` with **no host check and no counters**
  (**I4**): R360 closed the provider-ID half of that hatch and left the destination half open.
* The R360.6 auto-seed guard is proven only by a mock that raises where the real
  `GraphClient.execute_read` cannot — it swallows and returns `[]`, which the guard reads as
  "verified empty" (**I1**). This PR *added* `execute_read_strict` for exactly this
  distinction and used it at neither seeder call site.
* The one test named as proof that `--judge-provider bedrock` reaches Bedrock asserts
  `callable(caller)` (**I11**) — true for every provider, including a silent wrapper fallback.

The single Critical is **C1**: the `ab_judge` liveness probe accepts HTTP 200 from
`/v1/auth/status`, an endpoint this repo's own outage runbook records as lying. With the
Claude Max OAuth expired, the merge gate runs a "live" tier in which Stage-2 is dead on both
arms, both arms emit the identical deterministic answer, and the operator reads "the lever is
inert" from a run that measured nothing. That is worse than the quiet downgrade R360.2 set
out to fix, because the deterministic tier at least labels itself.

Five findings (**K1-K5**) were pre-confirmed before this review and deliberately excluded
from the specialists' scope. They are absent here **by design, not missed** — this report
does not restate them, and its findings were selected to be independent of them (e.g. **I5**
is the same false-green class as K1 but on the fallback counter and in a different module, so
it survives any fix to `app/main.py:1016`).

Nothing here blocks the transport contract itself. The recommended order is: **C1** (the
merge gate is currently unable to tell a live run from a dead one), then **I1** (the only
finding that can write to a live Aura graph), then the counter repairs **I2/I5/I6** as one
change with an `attempts == ok + failed` assertion, then **I4**.

## Critical Issues

### [C1] ab_judge liveness probe accepts HTTP 200 from an endpoint the repo documents as lying, so the merge gate runs a fake "live" tier

- **File:** `evals/harness/ab_judge.py:113`
- **Bug:** `_wrapper_up` returns `r.status == 200` from `/v1/auth/status` and never inspects
  the body. The repo's own outage runbook records that this endpoint returns `valid:true` +
  HTTP 200 on token *presence* alone, while every `POST /v1/chat/completions` fails 401 and
  the wrapper masks it as HTTP 500 "No response from Claude Code" — which is why CLAUDE.md
  tells you to verify with `/healthz/llm`, not `/v1/auth/status`. R360.2 fixed the URL and
  the CF-Access header; the auth-validity half is untouched. The new stub test at
  `tests/test_r360_2_ab_judge_tunnel_probe.py` hardcodes `status = 200` on a `_Resp` class
  with **no body at all**, so it structurally cannot exercise this.
- **Impact:** With the Claude Max OAuth expired, `_wrapper_up()` returns True, `run_ab` sets
  `live = True` (ab_judge.py:320), and the LIVE pairwise tier runs with Stage-2 dead on BOTH
  arms. Both arms emit the identical deterministic fallback answer, the grounded judge scores
  near-100% ties, and the operator reads "the lever is inert" from a run in which the gate
  never executed. Per CLAUDE.md this harness *is* the merge gate, so a false-live reading
  rejects real changes on evidence that measured nothing.
- **Suggested fix:** Make `_wrapper_up` prove a COMPLETION rather than a token file: POST a
  1-token `/v1/chat/completions` (`max_tokens=8`, body `reply OK`) with the same CF-Access
  headers and require a non-empty `choices[0].message.content`; treat HTTP 500 "No response
  from Claude Code" as down. Update the stub so a 200-with-dead-completions probe asserts
  False. Prior art exists in-repo: `.evalout/r319/live_ab.py:50` already comments that the
  live check must be a real POST because `/v1/auth/status` "is known to lie".

  Critical, 2 rated Important on the grounds that the blast radius is eval-only)

### [I1] R360.6 auto-seed guard is dead code in production — the real `execute_read` never raises, so a failed count reads as an empty graph

- **File:** `app/main.py:606` (guard), `tests/test_r360_6_auto_seed_guards.py:98` (false-green test)
- **Bug:** The guard wraps `client.execute_read("MATCH (n) RETURN count(n) AS c")` in
  `try/except Exception` and treats a raise as "skip-unverified". But `GraphClient.execute_read`
  (`app/graph/client.py:173-208`) catches **every** exception and returns `[]` on all three
  exits — it has no raising path. So the `except` arm at `app/main.py:610` is unreachable
  against the production client, and line 609 computes
  `int(([] or [{}])[0].get("c") or 0)` = `0`, the `if _node_count > 0` refusal at `:617` does
  not fire, and control falls through to `reason = "graph_empty"`. The same swallow defeats
  the KBMetadata probe one step earlier: the inline comment at `app/main.py:548` claims "a
  genuine exception from execute_read still propagates to the top-level handler below" — it
  cannot, for the same reason, so `current_seed` becomes `""` and control enters exactly the
  branch whose safety net is dead. `test_an_unreadable_node_count_is_not_seeded` passes only
  because a `MagicMock` raises `RuntimeError("connection reset")` (line 107) — behaviour the
  real client is pinned never to exhibit. **This PR added `GraphClient.execute_read_strict`
  (`app/graph/client.py:210`), which does raise, and used it at neither seeder call site.**
- **Impact:** AGENTS.md makes protecting live Aura nodes a hard rule and R360.6's stated
  purpose is exactly that. A transient non-ServiceUnavailable Neo4j read error at boot is
  misread as "verified empty" and triggers a full KB re-MERGE that SETs properties across a
  live, correctly-seeded graph — while a green test certifies the case is handled. This is the
  R329 shape (green diff, green test, zero runtime effect) applied to a write-safety guard.
  Bounded by: `run_seed(clear=False)` is MERGE-based (no deletions), and the whole path is
  behind `NEO4J_AUTO_SEED` — though note **I15**: the code default is ON when `NEO4J_URI` is
  set, contrary to the CLAUDE.md table.
- **Suggested fix:** Use the strict reader this PR added at **both** probes (`app/main.py:541`
  and `:606`), keeping the existing `except Exception -> return` arms so a failed read is
  treated as ignorance rather than emptiness. Additionally treat an empty result list as
  unverified (`if not _count_rows: return`) — a count query never legitimately returns no row.
  Then rewrite the test to drive a real `GraphClient` with `_run_read` patched to raise (as
  `tests/test_r360_12_verified_bug_fixes.py:103` already does), keeping the `[]` case as the
  primary parametrisation.

### [I2] An empty-but-successful wrapper completion is counted `primary_ok` and never reaches the Bedrock leg

- **File:** `app/engines/_graph_rag_impl.py:1018`
- **Bug:** `_openai_wrapper_complete_for_graph_rag` treats `response.error` as the only
  "primary failed" signal (line 1018). An HTTP-200 completion with empty content produces
  `error=None` — `app/llm/openai_wrapper_provider.py:620` does
  `text = msg.get("content") or ""`, and the not-logged-in / CLI-sentinel substring scans
  below it cannot match an empty string. All three downstream guards then pass **by
  construction**: `finish_reason` is `"stop"`, not `"length"`; `_looks_structurally_truncated("")`
  short-circuits `if not text: return False`; `_looks_incomplete_verdict("")` does the same.
  Execution reaches `record_result(STAGE2_PRIMARY, ok=True)` (lines 1237 and 1260) and
  `return response.text` (line 1262). The guards' own docstrings claim "Empty/whitespace text
  is handled upstream (validate_llm_output)" — it is handled *downstream*, in
  `_claude_max_enhance_answer` at ~`:8993`, which is **after both fallback blocks**.
- **Impact:** Two contract breaks. (1) The Bedrock leg stays dead for this mode: the fallback
  gates at `:8916` and `:8939` both test `text_raw is None`, and `""` is not None, so leg 2
  and the Gemini arm are skipped and the request degrades to the deterministic Stage-1 draft
  without a single Bedrock dial. (2) `primary_ok` increments for a call that produced nothing,
  so `/healthz/llm` reports `primary_attempts:1, primary_ok:1, fallback_attempts:0` — Stage-2
  reads perfectly healthy while Bedrock, which was armed and would have answered, was never
  dialled. The PR's central claim (the `_try_bedrock_fallback` docstring, `:897-911`) is that
  hoisting leg 2 lets "all three failure modes ... actually reach it"; the empty completion is
  a fourth, it is not hooked up, and it is the one this repo has already observed in
  production — see the Issue #42 comment at `:8989-8994`, "empty / whitespace-only polish is a
  failure, not a success".
- **Suggested fix:** Make emptiness a primary failure at the same gate as a transport error:
  change line 1018 to `if response.error or not (response.text or "").strip():`, passing
  `response.error or "empty_completion"` as the reason to `_try_bedrock_fallback`. Add a test
  driving `OpenAIWrapperResponse(text="", error=None, finish_reason="stop")` and asserting
  `primary_ok == 0` and `fallback_attempts == 1` — `tests/test_r360_stage2_transport_policy.py`
  exercises only `error="api_status_500"`, so this path is untested.

### [I5] `_try_bedrock_fallback` records `fallback_ok=True` for an answer it then discards, and records nothing when the call raises

- **File:** `app/engines/_graph_rag_impl.py:933`
- **Bug:** Two counting defects in one block. **(a)** Line 933 records
  `record_result(STAGE2_FALLBACK, ok=bool(bedrock_text))` *before* the quality checks; line
  939 may then discard the answer as structurally truncated and `return None`, with
  `fallback_ok` already incremented. **(b)** `record_attempt` is at line 923 and

  that matters, because an operator (or a future A/B) reading `fallback_ok > 0` concludes leg 2

  `return None` sites (empty text, truncation discard at `:944`, exception at `:953-959`) and
